## Post text

Addy Osmani, engineer at Google: "A decent model with a great harness beats a great model with a bad harness."

He shared what his harness actually does. Here's what you can copy:

1. Create AGENTS.md (or CLAUDE.md) in your project. Every time you correct the agent, add one line, like "use pnpm, not npm"

2. Block dangerous commands. In Claude Code settings, add rm -rf, git push --force and DROP TABLE to the deny list

3. Run tests after every change. Add a hook that runs your tests each time the agent edits a file, so it sees errors right away

4. Add to your rules: "never skip or delete a test to make it pass". Agents do this more often than you'd think

5. Add to your rules: "save long command output to a file and read only the end". Keeps the agent's memory clean

6. Before big tasks, ask it to write plan.md with the steps and a "done when" line. It ticks steps off as it goes

7. When it's done, open a fresh chat and ask it to review the changes against plan.md. Never let the same chat grade itself

His rule for all of it: every line in AGENTS.md should trace back to something that went wrong.

2. Agent = model + harness

The model is the brain. The harness is the job around the brain: which tools it can call, what it remembers, what it sees, and what happens before anything leaves the building.
Databricks lists the same parts, tools, memory, workspace and guardrails, and makes the point that harness design can matter as much as the underlying model. Fowler's article frames the work of building it as its own discipline: harness engineering.
That is the frame I used for this review. Viktor is a hire who shows up with the harness already built. You do not wire the tools, memory and approvals yourself. He shows up with them, and your job is to check whether each layer holds.

5. Layer 3: context
What an agent sees decides what it gets right, and what it should never see matters just as much.
