## Article: Harness, Loops, Graphs: What Each Layer Fixes and What It Breaks

You are not using your agent
You are its loop
It writes, you read
It says “done”, you check
It breaks something, you explain what broke
Then you type again
Almost every “autonomous” setup is a person quietly doing three jobs the system was supposed to do:
giving the model a place to work
telling it whether it was right
deciding what happens next
Those three jobs have names
Harness. Loop. Graph.
Most write-ups put them side by side like three tools on a shelf, and that is exactly why they feel confusing
They are not a menu
They are a ladder
Each layer exists because the one below it breaks in a specific, predictable way
Here are the 7 levels, what each one adds, what it fixes, and the exact failure that pushes you onto the next one
One example runs through all of it: a bug report comes in, and an agent has to fix it and open a PR
 
The 30-second map
 
 
And the ladder you climb with them:
 
 
 
Level 0: Chat
You paste the bug report
The model suggests a fix
You copy it into your editor, run the tests, paste the error back, and ask again
Look at who is doing what:
 
The model is the only part of this system not doing the hard work
It is a very smart function, and you are the entire program around it
That is fine for a one-off question
It is a disaster for anything you do twice
What breaks: you. You are the bottleneck on all three jobs at once
 
Level 1: Harness - give it hands
The first fix is obvious: let the agent touch the world
Shell. File access. A test runner. Git. A browser if the task needs one
Here is the cleanest definition of a harness I know:
Remove the model from your architecture diagram
Everything still on the page is the harness
Now our agent reads the repo, edits the file and runs the tests itself
No more copy-paste
But notice what the harness actually is
It is not “more tools”
Every tool you add is one more choice the model can get wrong
Ten narrow, documented tools beat forty overlapping ones
Give the agent the smallest environment that can finish the job
What breaks: it acts with no memory and no walls
Forty minutes in, the context is full of test logs
It gets compacted, and the agent forgets which fix it already tried, so it tries it again
And it has write access to everything, including the one config file it should never touch
 
Level 2: Harness - memory and walls
Two things are missing: state that outlives the context window, and limits that do not depend on the model behaving
Memory lives outside the model:
 
Plus git commits as checkpoints, and artifacts passed by reference instead of pasted transcripts
The context window is RAM
The harness is the disk
The model forgets. Files do not
Walls are everything that holds even when the model is wrong:
least-privilege permissions
an isolated worktree or sandbox
allow-lists for commands
a hard token and time budget
A wall is not an instruction
“Please do not touch migrations” is a wish
A permission the agent does not have is a wall
Now the agent can work for an hour, resume after a crash, and cannot wreck anything important
What breaks: it finishes with
“Fixed! All tests should pass now”
Should
The harness made the agent capable
Nothing in the system makes it correct
A capable agent with no check is just a faster way to be confidently wrong
 
Level 3: Loop - a check that can fail
A loop is four moves: produce, check, correct, repeat
Everyone focuses on “repeat”
The only part that matters is “check”
Without a check that can actually fail, “repeat” just means “repeat the mistake”
Not all evidence is equal, so rank it by how hard it is to fake:
 
 
The rule:
A check is only as strong as the weakest thing it accepts as proof
If your loop accepts “the model says it’s done”, your loop is self-report, no matter how many steps it has
Now write the check for our bug before the agent writes any code:
 
Look at the first line
A test that already passes before the fix proves nothing
The check has to be able to fail, and you should watch it fail once
There is a hidden bonus here
If you cannot write the check, you do not understand the task yet
Writing the check is writing the spec
What breaks: the agent fails, retries, and fails the same way six times
Because “red” is not feedback
It is a verdict
 
Level 4: Loop - feedback that converges
A verdict says “wrong”
Feedback says “wrong here, in this way, and you already tried that”
The simplest shape for it is the gap between what the agent expected and what the world did:
 
EXPECTED and SAW turn a red light into a direction
FENCE keeps the next attempt inside one file
DEAD ENDS is memory for the loop itself, so attempt 3 cannot quietly become attempt 1 again
Then the exits. A loop without them is not persistence, it is a cost leak:
 
The middle rule is the important one
When the agent gets the exact same result twice, it has stopped learning from the loop
More attempts will not help, because the missing piece is not effort
It is something the agent cannot see, or a task that was framed wrong
A loop can fix the work
A loop cannot fix the question
What breaks: the work becomes excellent, one unit at a time
But the real ticket said: fix the login loop, check whether the other two services use the same refresh helper, and update the docs
So the agent does it in a line, in one context
It fixes, then audits billing, then audits admin, then writes docs
The admin audit reads the billing audit’s conclusions and repeats them
Every step is correct
The whole is slow, serial, and holds one opinion
And no amount of loop tuning helps, because the problem is not inside any step
It is between them
 
Level 5: Graph - the shape of the work
A graph is three things:
 
Most arrows in a workflow are not dependencies
They are habits: the order in which someone happened to think of the steps
So run the early-start test on every arrow:
What would break if B started before A finished?
If the answer is “nothing”, the arrow is a habit, and every second spent waiting on it is waste
Start billing’s audit before the fix lands. Does anything break? No
Start the PR before the fix lands? Yes. That arrow is real
Here is our ticket, reshaped:
 
A few choices decide whether the graph helps or just looks impressive:
Cut where things fail separately. If two pieces can break for different reasons, they are two nodes. If they always break together, they are one
Give every worker its own room. Four agents in one shared context are not a team. They are one agent wearing four hats, and the first opinion written becomes everyone’s opinion
Ask the same-answer question. If the step should give the same output every time it sees the same input, it is code. Merging, sorting, deduping, counting. Models are for steps where a different answer could also be right
Put a gate where work leaves a node, not at the very end, where every mistake is already mixed with everything else
And here is how the two layers fit together:
A loop asks “is this piece right?” A graph asks “are these the right pieces?”
You need both. Every FIX and AUDIT node above runs its own Level 4 loop
What breaks: two things, both new
One audit fails and the whole batch runs again. The three good results come back different. Not better, just different, and now they all need checking again
And everything that passes a gate moves at the same speed. A typo in the docs and a change to the auth flow get the exact same treatment
 
Level 6: Graph - gates and return paths
Freeze what passed
Once a node’s output gets through its gate, it becomes read-only
Nothing downstream is allowed to reopen it
When something fails, only the failed node runs again, with its feedback, and the frozen results stay exactly as they were
Every rerun of good work is a fresh chance to break it, and you get nothing in return
Gate on the price of undo
Confidence is the model grading its own exam
A better question: if this is wrong, what does it cost to take it back?
 
 
The last tier has no score attached to it at all
Not 0.95, not 0.99
There is no number for the model to beat, so there is nothing to argue with
Inside the first two tiers, read evidence in ladder order: tests, then the trace, then the second opinion, and the model’s own confidence dead last
The model labels the change. Code decides what the label unlocks
The model may say “this touches auth”
Whether “auth” means one approval or two is written in code, before the run starts
Spend your attention only where undo does not exist
You are the most expensive node in the graph and the slowest one
Put yourself where a mistake cannot be taken back, and nowhere else
In our example: the docs change ships itself, the auth fix waits for one approval on the PR, and you never read the audits unless they disagree
What breaks: it works
And next week, the same kind of bug arrives
The agent makes the same wrong first attempt, burns the same two retries, and lands on the same fix
The system is fast and has no memory across runs
You are paying it to learn the same lesson twice
 
Level 7: The system learns, on every layer
Most people who get here add one feedback edge back to the planner and stop
But every failure belongs to a layer, and a lesson only sticks when it lands on the layer that owns it:
 
Put a lesson on the wrong layer and it turns into advice
“Be careful not to duplicate work” in a prompt is a hope
A split rule in the splitter is structure
And a lesson is a constraint, not a transcript
You do not feed last week’s logs into next week’s run
You feed it the one rule those logs taught you
The test for Level 7 is simple:
The same class of failure never costs you twice
 
Which level are you on?
 
 =
Find your first symptom from the top
That is your next level. Not the one after it
 
How to climb
You cannot skip levels
Ten agents with no checks do not give you ten times the output. They give you ten times the cleanup
A perfect loop with no harness has nowhere to run its tests
But you design from the middle
Before you build anything, write the Level 3 check on paper
If you can say what green means, you know which tools the harness needs to prove it, and you know where the graph should put its gates
If you cannot say what green means, no layer will save you
And you do not need to reach the top
Most tasks are done at Level 4
Climb only when the failure at your current level costs more than building the next one
 
The short version
A harness makes the agent capable
A loop makes it honest
A graph makes it organized
Learning makes it better than yesterday
Skip a layer and you become the missing piece
The goal was never an agent that does not need you
It is a system that needs you once, at the right place
